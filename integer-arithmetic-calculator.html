Input format & operation notes

Operand format: decimal (e.g. -17), hex with 0x prefix (e.g. 0xFF), or binary with 0b prefix (e.g. 0b1010). A leading - is allowed on any base.

~A and -A use Operand A only; Operand B is disabled and ignored.

<< and >> use Operand B as a raw shift count (not wrapped into A's type). A count outside [0, width) for a given type is undefined behavior and is reported as such, not computed.

/ and % truncate toward zero and take the sign of the dividend, matching C99 / C++11 integer division. Division or modulo by zero is undefined behavior for integers (it traps or crashes at runtime — it does not produce infinity or NaN the way floating-point division does).

Notes

Wrapped — the unsigned result didn't fit the type's width, so it was reduced modulo 2ⁿ. This is well-defined behavior: arithmetic on unsigned types in C/C++ is always modulo 2ⁿ, never undefined. Overflow* — the signed result didn't fit the type's range. Signed integer overflow is undefined behavior per the C/C++ standard; the value shown is the two's-complement wraparound nearly every real compiler produces without overflow sanitizers or -ftrapv — not a guarantee. Undefined — division/modulo by zero, or a shift count outside [0, width) for that type. No sane numeric result exists; real code doing this typically crashes or traps. Right shift of a negative signed value is implementation-defined by the standard; this calculator assumes the sign-extending arithmetic shift used by GCC, Clang, and MSVC. Left-shifting a value across a signed type's sign bit is undefined behavior before C++20, and well-defined (wraps) from C++20 onward. Compare to C compares each type's own correctly interpreted result value against C directly — it does not simulate real C/C++'s "usual arithmetic conversions" between A and B themselves. Use the Mixed Types tab to see those conversions play out. Mixed Types simulates what real C/C++ does when A and B have different declared types. Anything narrower than int (8/16-bit) is promoted to a plain signed int before any arithmetic happens — so mixing signed/unsigned int8_t/int16_t types usually doesn't trigger the bug in real code. At int rank and wider, mixing signedness converts one operand to match the other via the "usual arithmetic conversions": at equal rank the signed side converts to unsigned first — add (int32_t)-1 + (uint32_t)0 and you get 4294967295, not -1, because -1 is reinterpreted as UINT32_MAX before the addition runs. When the signed type has strictly greater rank it wins instead — (int64_t)-1 combined with a uint32_t stays signed and negative, because int64_t can represent every uint32_t value. Shift operators are exempt: they never merge A and B into a common type — only A's promoted type sets the result, and B is just a promoted count.
